# Подэтап 4.3: чтение и поиск профилей

Здесь описан текущий вариант кода после упрощения моделей и поиска. В этом подэтапе Application задаёт сценарии чтения, а репозитории и шлюз Identity предоставляет через порты. Реальные адаптеры хранения и подписи курсора относятся к следующему этапу.

## Какие ответы возвращаем

`TeacherProfileView` и `StudentProfileView` — общие модели профиля для собственного просмотра, публичного просмотра и просмотра через подтверждённую связь. Модель ответа содержит данные профиля и вычисленный возраст, но не дату рождения и не дату создания профиля. Правила доступа остаются разными: общий DTO сам по себе доступ не разрешает.

`TeacherProfileSummary` и `StudentProfileSummary` — короткие данные для списка связей: идентификатор и отображаемое имя. Они не заменяют полное чтение профиля.

## Чтение одного профиля

В [ProfileQueryService](../../backend/src/main/java/io/github/edtechdevelopment/tutoring/application/profile/service/ProfileQueryService.java) находятся несколько отдельных сценариев.

- `findTeacherProfile` и `findStudentProfile` читают профиль текущего пользователя. Доверенный вызывающий код должен передать их `userId` текущего аккаунта.
- `findPublicTeacherProfile` и `findPublicStudentProfile` читают профиль по переданному идентификатору и проверяют через Identity, что аккаунт активен. Для неактивного аккаунта возвращают пустой результат.
- `findLinkedStudentProfile` и `findLinkedTeacherProfile` сначала проверяют существование связи в нужном направлении, затем читают профиль и проверяют активность аккаунта.
- `requireTeacherProfile` проверяет наличие профиля преподавателя.
- `findTeacherSummaries` и `findStudentSummaries` запрашивают короткие данные сразу для переданного множества пользователей. Пустое множество сразу даёт пустую карту.

Во всех сценариях возраст запрашивается у Identity на текущую дату UTC. Tutoring получает только число возраста. Если для существующего профиля Identity не вернул возраст, сервис считает это несогласованностью данных и сообщает об ошибке.

## Что такое кандидат поиска

`PublicProfileSearchCandidate` — небольшой объект с `userId` и `createdAt`. Это не ответ пользователю и не отдельная копия даты в доменной модели. Репозиторий использует его, чтобы сообщить Application, какой профиль идёт следующим в отсортированном списке. Полная модель профиля пока не загружается.

`createdAt` хранится в самой доменной модели `TeacherProfile` или `StudentProfile`. Репозиторий может вернуть его как часть кандидата, а когда пользователь обновляет профиль, Application передаёт прежнее значение в новую модель. Так обновление не перемещает профиль в списке.

`ProfileNameData` — другой небольшой результат репозитория. Он нужен там, где достаточно `userId` и `displayName`, например для списка связей.

## Как устроен поиск страницами

В [PublicProfileSearchService](../../backend/src/main/java/io/github/edtechdevelopment/tutoring/application/profile/service/PublicProfileSearchService.java) методы `searchTeachers` и `searchStudents` выполняют поиск для своего типа профиля. Их порядок работы одинаков:

1. Проверить запрос и, если он пришёл с курсором, проверить курсор.
2. Попросить репозиторий выдать следующую порцию кандидатов. Репозиторий применяет фильтр предмета и отдаёт кандидатов по `createdAt DESC`, затем `userId DESC`.
3. Одним запросом передать набор их `userId` в Identity и получить активные аккаунты; вторым пакетным запросом получить возраст активных аккаунтов.
4. Оставить кандидатов, которые подходят по активности и диапазону возраста. Если их пока мало, взять следующую порцию кандидатов и повторить проверки.
5. Когда набралось 21 подходящий кандидат или каталог закончился, оставить первые 20. Дополнительный кандидат нужен, чтобы точно понять, есть ли следующая страница. Размер страницы всегда 20 и не передаётся в запросе.
6. Только для профилей, которые попадут в страницу ответа, одним batch-вызовом загрузить доменные модели и преобразовать их в короткие `TeacherProfileCardView` или `StudentProfileCardView`.

Такой порядок нужен потому, что возраст и активность находятся в Identity, а предметы и остальные данные профиля — в Tutoring. Фильтрацию можно выполнить между ними, не запрашивая каждый аккаунт и полный профиль по одному.

## Курсор простыми словами

Курсор нужен, чтобы следующий запрос продолжил список после последнего уже показанного профиля. Например, первая страница закончилась профилем с `createdAt = T` и `userId = U`; курсор запоминает эту позицию. Следующая страница получает профили, которые идут строго после неё в порядке сортировки. `userId` разрешает ситуацию, когда у нескольких профилей одинаковый `createdAt`.

Внутри `PublicProfilePageCursor` хранит позицию (`createdAt`, `userId`) и дату, на которую вычислялся возраст. Дата возраста остаётся прежней на следующих страницах, поэтому человек не меняет возраст посреди просмотра длинного списка, если запросы пришлись на разные дни. Курсор стоит на последней показанной карточке: дополнительная 21-я запись будет проверена снова при следующем запросе. Если фильтры отсеяли строки между 20-й и 21-й подходящими карточками, они тоже могут провериться повторно.

Повторная проверка этой небольшой области — намеренное допущение MVP. Lookahead-кандидат позволяет точно сообщить, есть ли продолжение; курсор на последней показанной карточке гарантирует, что первая карточка следующей страницы не потеряется. Пока мы принимаем повторное чтение lookahead-кандидата и возможных отфильтрованных строк после границы страницы, чтобы не хранить промежуточный результат между запросами.

`PublicProfileCursorCodec` — выходной порт Application. Сервис просит его разобрать входной курсор или создать курсор для следующей страницы. Infrastructure позже реализует подпись и проверку. Подпись не даёт клиенту незаметно подменить позицию или фильтры. Курсор связывается с типом профиля и фильтрами; размер страницы фиксирован и не хранится в курсоре.

## Почему в сервисе нет общего метода с параметрами типов

Поиск преподавателей и учеников написан через обычные методы и конкретные типы. Общая часть находится в `findCandidatePage`, которая выбирает подходящий репозиторий по типу профиля и возвращает общие данные кандидатов. После этого каждый публичный метод загружает свой тип доменной модели и свой DTO. Так код проще читать и в нём не нужны `R`, `V`, `BiFunction` и общий метод с несколькими параметрами типов.

## Основные изменения этапа

- `createdAt` добавлен в доменные профили и сохраняется при регистрации, восстановлении модели и обновлении.
- Удалены `ProfileSearchRow`, `TeacherProfileSearchRow`, `StudentProfileSearchRow` и `ProfileSummaryRow`.
- Вместо них используются `PublicProfileSearchCandidate` и `ProfileNameData` с конкретным назначением.
- Удалены отдельные self/public DTO; сценарии используют общие `TeacherProfileView` и `StudentProfileView`, сохраняя раздельные проверки доступа.
- Поиск возвращает отдельные короткие карточки; полный профиль открывается отдельным публичным запросом.
- Размер страницы поиска фиксирован в 20 результатов; из фильтров убран пользовательский `limit`.
- Алгоритм поиска больше не использует обобщённый метод с параметрами типов.

# API профилей и расписания

Статус: черновик для согласования  
Версия контракта: `0.3.0`  
Базовый URL: `/api/v1`

Документ описывает контракт между frontend и backend для первой версии регистрации, профилей и расписания. Физическая модель PostgreSQL, вход, восстановление и изменение пароля в этот контракт не входят.

## 1. Предметная модель

### User

`User` — зарегистрированный аккаунт человека в системе. При создании обязательны уникальный email и пароль.

```text
User
  id
  firstName
  lastName
  email
```

Пароль поступает только в команде регистрации. Он не возвращается как атрибут `User`: identity-модуль сохраняет необратимый хеш пароля.

### Teacher

`Teacher` представляет пользователя в роли преподавателя. Отдельных имени и контактов у него нет: они берутся из связанного `User`.

Один пользователь имеет не более одного собственного `Teacher`. При этом он может учиться у любого количества других преподавателей. Например, Алексей может преподавать Анне и одновременно учиться у Марии.

```text
Teacher
  user: User
  students: List<User>
```

Отдельной сущности `Student` в первой версии нет. Ученик — это `User`, который связан с преподавателем или участвует в занятии как ученик.

### LessonOccurrence

`LessonOccurrence` — конкретное занятие в календаре.

```text
LessonOccurrence
  id
  teacher: Teacher
  students: List<User>
  startAt: Instant
  endAt: Instant
  status: LessonStatus
  format: LessonFormat
```

`LessonStatus`:

- `SCHEDULED` — запланировано;
- `COMPLETED` — проведено;
- `CANCELLED` — отменено.

`LessonFormat`:

- `INDIVIDUAL` — ровно один ученик;
- `GROUP` — один или несколько учеников.

Формат задаётся явно. Групповое занятие с одним участником остаётся групповым.

## 2. Общие правила API

- Формат данных — JSON, имена полей — `camelCase`.
- Все идентификаторы передаются как непрозрачные строки. Frontend не должен считать их числами или самостоятельно разбирать.
- `teacherUserId` — это `User.id` человека, у которого создан `Teacher`.
- `studentUserId` — это `User.id` участника в роли ученика.
- Время передаётся по RFC 3339 с датой и часовым смещением, например `2026-09-07T18:00:00+03:00`.
- Backend возвращает время в UTC, например `2026-09-07T15:00:00Z`.
- `endAt` всегда позже `startAt`.
- Неизвестные поля в запросах не принимаются.
- Успешные ответы возвращаются без дополнительной обёртки `data`.
- Авторизация предварительно передаётся через Bearer token. Способ выдачи токена будет определён в модуле identity.
- Email обязателен и уникален без учёта регистра.
- Пароль обязателен при регистрации, содержит 8–128 символов и никогда не возвращается или не записывается в логи.

## 3. Модели ответов

### UserSummary

Краткое представление человека без контактных данных:

```json
{
  "id": "u_001",
  "firstName": "Алексей",
  "lastName": "Иванов"
}
```

### UserResponse

Полный доступный профиль:

```json
{
  "id": "u_001",
  "firstName": "Алексей",
  "lastName": "Иванов",
  "email": "alex@example.com"
}
```

`email` обязателен. Поле `password` и хеш пароля в ответы не включаются.

### TeacherResponse

```json
{
  "user": {
    "id": "u_001",
    "firstName": "Алексей",
    "lastName": "Иванов"
  }
}
```

Список учеников не вкладывается в ответ преподавателя и запрашивается отдельно.

## 4. Пользователи и преподаватели

### Зарегистрировать пользователя

```http
POST /api/v1/users
```

```json
{
  "firstName": "Анна",
  "lastName": "Петрова",
  "email": "anna@example.com",
  "password": "example-password"
}
```

Обязательны `firstName`, `email` и `password`. `lastName` необязателен и при пропуске сохраняется как пустая строка. Email нормализуется и проверяется на уникальность без учёта регистра.

Ответ: `201 Created` и `UserResponse`.

Пароль присутствует только в запросе. Backend хеширует его и никогда не возвращает исходное значение или хеш. Повтор уже занятого email возвращает `409 EMAIL_ALREADY_EXISTS`.

### Получить профиль

```http
GET /api/v1/users/{userId}
```

Ответ: `200 OK` и `UserResponse`.

### Изменить профиль

```http
PATCH /api/v1/users/{userId}
```

```json
{
  "firstName": "Александр"
}
```

Переданные поля заменяются, остальные сохраняются. `lastName: ""` очищает фамилию. Email нельзя очистить значением `null`. Пароль через этот endpoint не меняется; для него потребуется отдельный endpoint identity. Пустое тело запрещено.

Ответ: `200 OK` и обновлённый `UserResponse`.

### Сделать пользователя преподавателем

```http
PUT /api/v1/teachers/{teacherUserId}
```

Тело отсутствует.

- `201 Created` и `TeacherResponse`, если `Teacher` создан;
- `200 OK` и существующий `TeacherResponse`, если пользователь уже преподаватель.

Повторный запрос не очищает список учеников.

### Получить преподавателя

```http
GET /api/v1/teachers/{teacherUserId}
```

Ответ: `200 OK` и `TeacherResponse`. Если `User` существует, но его `Teacher` не создан, возвращается `404 Not Found`.

## 5. Связи преподавателя с учениками

### Получить учеников преподавателя

```http
GET /api/v1/teachers/{teacherUserId}/students?cursor={cursor}&limit=50
```

```json
{
  "items": [
    {
      "id": "u_002",
      "firstName": "Анна",
      "lastName": "Петрова"
    }
  ],
  "nextCursor": null
}
```

`cursor` необязателен. `limit` по умолчанию равен 50, максимальное значение — 100. `nextCursor: null` означает конец списка.

### Пригласить нового ученика

```http
POST /api/v1/teachers/{teacherUserId}/student-invitations
```

```json
{
  "email": "anna@example.com"
}
```

Преподаватель не создаёт чужой аккаунт и не назначает ученику пароль. Backend создаёт приглашение, а отправка письма выполняется модулем `notifications`.

Ответ: `201 Created`:

```json
{
  "id": "inv_001",
  "teacher": {
    "user": {
      "id": "u_001",
      "firstName": "Алексей",
      "lastName": "Иванов"
    }
  },
  "email": "anna@example.com",
  "status": "PENDING",
  "expiresAt": "2026-09-13T15:00:00Z"
}
```

Статусы приглашения: `PENDING`, `ACCEPTED`, `EXPIRED`, `CANCELLED`. Повтор активного приглашения на тот же email возвращает `409 INVITATION_ALREADY_PENDING`.

Если аккаунта ещё нет, человек сначала регистрируется через `POST /users`, самостоятельно задавая пароль. Затем аутентифицированный пользователь принимает приглашение:

```http
POST /api/v1/student-invitations/{invitationId}/accept
```

Тело отсутствует. Текущий пользователь может принять только приглашение, отправленное на email его аккаунта. Ответ: `204 No Content`. Принятие атомарно добавляет его в `Teacher.students`.

### Добавить существующего человека в ученики

```http
PUT /api/v1/teachers/{teacherUserId}/students/{studentUserId}
```

Тело отсутствует. Ответ: `204 No Content`. Повторный запрос безопасен и возвращает тот же результат.

Преподаватель не может добавить самого себя в собственный список учеников. Пользователь, который сам является преподавателем, может быть учеником другого преподавателя.

### Убрать человека из учеников

```http
DELETE /api/v1/teachers/{teacherUserId}/students/{studentUserId}
```

Ответ: `204 No Content`.

Операция удаляет только текущую связь. Она не удаляет `User`, его собственный `Teacher` или существующие занятия, включая будущие.

### Получить преподавателей пользователя

```http
GET /api/v1/users/{userId}/teachers?cursor={cursor}&limit=50
```

```json
{
  "items": [
    {
      "user": {
        "id": "u_003",
        "firstName": "Мария",
        "lastName": "Смирнова"
      }
    }
  ],
  "nextCursor": null
}
```

Список строится по текущим связям `Teacher.students`, независимо от наличия занятий.

## 6. Календарь

### Календарь преподавателя

```http
GET /api/v1/teachers/{teacherUserId}/lessons?from={from}&to={to}&status={status}
```

Возвращает занятия, которые пользователь проводит как преподаватель.

### Календарь ученика

```http
GET /api/v1/users/{userId}/learning-lessons?from={from}&to={to}&status={status}
```

Возвращает занятия, в которых пользователь участвует как ученик. Пользователю не требуется отдельная сущность `Student`.

Для обоих календарей:

- `from` и `to` обязательны;
- `status` необязателен;
- интервал имеет форму `[from, to)`: `from` включён, `to` не включён;
- максимальная длина интервала — 93 суток;
- занятие попадает в результат, если `startAt < to` и `endAt > from`;
- сортировка: сначала `startAt`, затем `id`;
- пагинации нет, сервер возвращает полный список за выбранный интервал;
- без фильтра статуса возвращаются в том числе отменённые занятия.

Пример запроса недели по московскому времени:

```http
GET /api/v1/teachers/u_001/lessons?from=2026-09-06T21%3A00%3A00Z&to=2026-09-13T21%3A00%3A00Z
```

Ответ преподавателю:

```json
{
  "from": "2026-09-06T21:00:00Z",
  "to": "2026-09-13T21:00:00Z",
  "items": [
    {
      "id": "l_001",
      "teacher": {
        "user": {
          "id": "u_001",
          "firstName": "Алексей",
          "lastName": "Иванов"
        }
      },
      "students": [
        {
          "id": "u_002",
          "firstName": "Анна",
          "lastName": "Петрова"
        }
      ],
      "startAt": "2026-09-07T15:00:00Z",
      "endAt": "2026-09-07T16:00:00Z",
      "status": "SCHEDULED",
      "format": "INDIVIDUAL"
    }
  ]
}
```

В календаре ученика элемент списка имеет сокращённый вид:

```json
{
  "id": "l_002",
  "studentUserId": "u_001",
  "teacher": {
    "user": {
      "id": "u_003",
      "firstName": "Мария",
      "lastName": "Смирнова"
    }
  },
  "startAt": "2026-09-08T09:00:00Z",
  "endAt": "2026-09-08T10:00:00Z",
  "status": "SCHEDULED",
  "format": "GROUP"
}
```

Другие участники группового занятия ученику пока не раскрываются.

### Получить одно занятие

Для преподавателя:

```http
GET /api/v1/teachers/{teacherUserId}/lessons/{lessonId}
```

Для ученика:

```http
GET /api/v1/users/{userId}/learning-lessons/{lessonId}
```

Преподаватель получает полный состав. Ученик получает сокращённое представление без остальных участников.

## 7. Управление занятием

### Создать занятие

```http
POST /api/v1/teachers/{teacherUserId}/lessons
```

Индивидуальное занятие:

```json
{
  "studentUserIds": ["u_002"],
  "startAt": "2026-09-07T18:00:00+03:00",
  "endAt": "2026-09-07T19:00:00+03:00",
  "format": "INDIVIDUAL"
}
```

Групповое занятие:

```json
{
  "studentUserIds": ["u_002", "u_004"],
  "startAt": "2026-09-07T18:00:00+03:00",
  "endAt": "2026-09-07T19:00:00+03:00",
  "format": "GROUP"
}
```

Правила:

- преподаватель определяется по `teacherUserId` из URL;
- Teacher должен существовать;
- все участники должны входить в текущий список учеников Teacher;
- список участников не может быть пустым или содержать повторы;
- преподаватель не может быть учеником собственного занятия;
- `INDIVIDUAL` требует ровно одного ученика;
- `GROUP` требует минимум одного ученика;
- начальный статус всегда `SCHEDULED`;
- пересечения занятий в первой версии разрешены.

Ответ: `201 Created` и полное представление занятия.

### Перенести или изменить занятие

```http
PATCH /api/v1/teachers/{teacherUserId}/lessons/{lessonId}
```

Перенос:

```json
{
  "startAt": "2026-09-08T15:00:00Z",
  "endAt": "2026-09-08T16:00:00Z"
}
```

Изменение индивидуального занятия на групповое:

```json
{
  "format": "GROUP",
  "studentUserIds": ["u_002", "u_004"]
}
```

Правила PATCH:

- изменять можно только занятие в статусе `SCHEDULED`;
- при изменении времени `startAt` и `endAt` передаются вместе;
- `studentUserIds` заменяет весь состав, а не дополняет его;
- непереданные поля сохраняются;
- формат и состав проверяются по итоговому состоянию;
- смена преподавателя не поддерживается;
- изменение выполняется атомарно;
- `lessonId` сохраняется при переносе.

Ответ: `200 OK` и обновлённое занятие.

### Отменить или завершить занятие

```http
PUT /api/v1/teachers/{teacherUserId}/lessons/{lessonId}/status
```

Отмена:

```json
{
  "status": "CANCELLED"
}
```

Завершение:

```json
{
  "status": "COMPLETED"
}
```

Разрешённые переходы:

```text
SCHEDULED -> CANCELLED
SCHEDULED -> COMPLETED
```

Завершить занятие можно только после `endAt` по времени backend. Повторная установка текущего конечного статуса возвращает успешный ответ. Возврат в `SCHEDULED` и переход между `CANCELLED` и `COMPLETED` пока не поддерживаются.

Отменённое занятие не удаляется и остаётся в календаре со статусом `CANCELLED`.

## 8. Ошибки

Единый формат ошибки:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Для индивидуального занятия нужен ровно один ученик",
  "fieldErrors": [
    {
      "field": "studentUserIds",
      "code": "FORMAT_PARTICIPANTS_MISMATCH",
      "message": "Измените состав или формат занятия"
    }
  ]
}
```

`fieldErrors` всегда является массивом. Для общей ошибки он пустой. Frontend принимает решение по `code`, а не по тексту `message`.

| HTTP | code | Значение |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Неверные поля или нарушен инвариант |
| 400 | `INVALID_INTERVAL` | Неверные `from`/`to` или интервал больше 93 суток |
| 409 | `EMAIL_ALREADY_EXISTS` | Аккаунт с таким email уже зарегистрирован |
| 401 | `UNAUTHENTICATED` | Нет действующей сессии |
| 403 | `FORBIDDEN` | Действие запрещено |
| 404 | `NOT_FOUND` | Ресурс отсутствует или недоступен пользователю |
| 409 | `INVALID_LESSON_STATE` | Текущее состояние занятия не допускает операцию |
| 409 | `STUDENT_NOT_LINKED` | Новый участник не связан с преподавателем |
| 409 | `LESSON_NOT_ENDED` | Занятие ещё нельзя завершить |
| 409 | `INVITATION_ALREADY_PENDING` | Активное приглашение уже существует |
| 409 | `INVALID_INVITATION` | Приглашение не принадлежит текущему пользователю или недействительно |
| 409 | `INVITATION_EXPIRED` | Срок приглашения истёк |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка backend |

Примеры кодов конкретных полей:

- `FORMAT_PARTICIPANTS_MISMATCH`;
- `SELF_TEACHING_NOT_ALLOWED`;
- `MUST_BE_AFTER_START`.

## 9. Правила доступа

- Пользователь читает и изменяет собственный профиль. Работа с чужим профилем требует отдельного разрешения.
- Преподаватель или его редактор управляет списком учеников и своими занятиями.
- Новый ученик сам регистрирует аккаунт и задаёт пароль, затем принимает приглашение на свой email.
- Связанный ученик не получает доступ ко всему календарю преподавателя.
- Преподаватель видит занятия с учеником через собственный календарь, но не видит занятия этого ученика у других преподавателей.
- Знание идентификатора не считается разрешением на доступ или создание связи.
- Недоступный ресурс возвращается как `404`, если нельзя раскрывать факт его существования.

Конкретная модель аккаунтов, ролей авторизации и назначения редакторов будет определена в модуле identity.

## 10. Границы первой версии

В контракт пока не входят:

- регулярные занятия и `LessonSeries`;
- постоянная сущность учебной группы;
- предмет, цвет занятия, ссылка на видеозвонок и заметки;
- удаление занятия;
- запрет пересечений расписания;
- push-обновления календаря;
- защита от одновременного редактирования через версию записи;
- вход, выход, обновление токена, восстановление и изменение пароля;
- повторная отправка и отмена приглашения.

Предлагаемые backend-модули:

- `identity` владеет регистрацией, email, хешем пароля и будущими сессиями;
- `people` владеет профилем `User`, `Teacher` и связями преподавателя с учениками;
- `scheduling` владеет `LessonOccurrence` и обращается к публичному интерфейсу `people` для проверки пользователей и связей.
- `notifications` позже будет доставлять письма с приглашениями.

Машиночитаемая спецификация: `scheduling.openapi.json`. Она является точным источником DTO и маршрутов; этот документ объясняет её разработчику.

# Tutoring — этап 1. Границы и каталог сценариев

Статус: согласованный вариант этапа 1
Дата фиксации: 2026-09-13
Актуальное решение: дата рождения хранится только в Identity и доступна владельцу в данных аккаунта. Учебные профили показывают вычисленный возраст и контактные данные всем посетителям активного профиля без связи. Контактный email профиля не требует подтверждения.
Синхронизация от 2026-09-24: уточнены доступ к справочнику и приглашениям, `attachedAt` и чтение статуса без записи. Детали Infrastructure/HTTP приведены в `TUTORING_STAGE_5_INFRASTRUCTURE_AND_PRESENTATION.md`.

## 1. Назначение документа

Документ фиксирует функциональные границы backend-модуля `Tutoring`, владельцев данных, участников, основные инварианты и полный каталог сценариев первой версии.

На этом этапе не фиксируются окончательные Java-сигнатуры, структура пакетов, HTTP DTO и SQL-схема. Они должны проектироваться далее на основании описанных здесь сценариев и границ.

## 2. Архитектурный контекст

Backend является модульным монолитом на Spring Boot и Spring Modulith:

```text
backend
├── identity
├── tutoring
├── scheduling
├── workflows
└── notifications
```

Модули работают в одном приложении, но каждый изменяемый объект и каждая таблица имеют ровно одного владельца. Межмодульное взаимодействие выполняется только через публичные API и согласованные события.

Основные направления зависимостей:

```text
Tutoring   → Identity API
Scheduling → Tutoring API
Workflows  → Identity API + Tutoring API + Scheduling API
Tutoring   → Notifications API или публичное событие доставки
```

Запрещён цикл:

```text
Tutoring ↔ Scheduling
```

## 3. Назначение Tutoring

`Tutoring` управляет участием зарегистрированных пользователей в учебном процессе.

Модуль отвечает на вопросы:

- существует ли учебный профиль преподавателя или ученика;
- какие данные пользователь указал для конкретного учебного профиля;
- какие предметы пользователь указал как направления преподавания или изучения;
- существует ли переданный `SubjectCode` в справочнике;
- кому преподаватель отправил приглашение;
- каков статус приглашения;
- какому зарегистрированному пользователю принадлежит приглашение;
- принял или отклонил пользователь приглашение;
- связаны ли преподаватель и ученик;
- каких учеников преподаватель может выбирать для уроков;
- какие контактные данные входят в публичный профиль;
- как показывать вычисленный возраст в профиле активного пользователя.

`Tutoring` не отвечает на вопросы:

- как пользователь регистрируется, входит в систему и восстанавливает доступ;
- как проверяется подпись JWT;
- какой у пользователя пароль, refresh token или статус аккаунта;
- когда проводится урок;
- пересекаются ли интервалы уроков;
- завершён, отменён или пропущен урок;
- сколько уроков провёл преподаватель или посетил ученик;
- как физически доставляется email;
- можно ли удалить связь без обработки будущих уроков.

## 4. Роли, пользователь и учебные профили

### 4.1 Владение ролями

Образовательные роли являются частью состояния аккаунта и принадлежат `Identity.User`:

```text
Identity.User
├── id: UUID
├── email: Email
├── pendingEmail: Email?
├── firstName: String
├── lastName: String
├── birthDate: LocalDate
├── passwordHash
├── status: UserStatus
└── roles: Set<UserRole>
```

```text
UserRole
├── TEACHER
└── STUDENT
```

Роль отвечает на вопрос, в каком качестве пользователь зарегистрирован и к каким функциям приложения он может получать доступ. Профиль отвечает на вопрос, какие учебные и контактные данные пользователь указал для работы в этом качестве.

`TeacherProfile` и `StudentProfile` не наследуют `Identity.User`. Они хранят только `userId` как логическую межмодульную ссылку.

### 4.2 Обязательный выбор роли

При регистрации пользователь обязан выбрать хотя бы одну роль.

Допустимые наборы:

```text
{TEACHER}
{STUDENT}
{TEACHER, STUDENT}
```

Пустой набор запрещён.

### 4.3 Роль и профиль создаются вместе

После выбора роли frontend сразу показывает форму соответствующего профиля. Если выбраны обе роли, пользователь заполняет обе формы.

Регистрация должна соблюдать двусторонний инвариант:

```text
TEACHER входит в User.roles
⇔ TeacherProfile существует

STUDENT входит в User.roles
⇔ StudentProfile существует
```

Роль без соответствующего профиля и профиль без соответствующей роли являются запрещёнными состояниями.

Поскольку регистрация изменяет `Identity` и `Tutoring`, её координирует внешний `RegistrationWorkflow`. Оба изменения фиксируются одной PostgreSQL-транзакцией. Identity получает роли, но не получает profile DTO и не проверяет существование профилей. Tutoring получает `userId` и profile data, но не изменяет роли.

`POST /api/v1/auth/register` обслуживает `workflows.registration.presentation.RegistrationController`. Размещать этот endpoint в `identity.presentation` нельзя: иначе Identity начнёт зависеть от Workflows, а Workflows уже зависит от публичного API Identity.

### 4.4 Добавление второй роли

Если пользователь зарегистрирован только как преподаватель, в области профиля ученика frontend показывает:

```text
Профиль ученика
Вы ещё не зарегистрированы как ученик.

[Стать учеником]
```

Кнопка открывает форму ученика. Роль не добавляется до успешного заполнения и проверки формы.

После отправки формы внешний onboarding workflow атомарно:

1. проверяет активность пользователя;
2. валидирует данные нового профиля;
3. добавляет вторую роль в `Identity`;
4. создаёт профиль в `Tutoring`;
5. фиксирует оба изменения одной транзакцией;
6. инициирует обновление access JWT, чтобы новый токен содержал обе роли.

Зеркальный сценарий применяется, когда ученик решает стать преподавателем.

Прямой пользовательский endpoint добавления `TEACHER` или `STUDENT` без профиля не предоставляется. Внутренний контракт добавления роли доступен только workflow-компоненту.

В первой версии разрешается только добавление второй образовательной роли. Удаление роли и профиля не входит в объём, поскольку потребует отдельного workflow для проверки связей, приглашений и уроков.

## 5. Владение данными

| Данные | Владелец | Назначение |
|---|---|---|
| `User`, `email`, `pendingEmail`, `firstName`, `lastName` | Identity | Учётная запись и вход |
| `birthDate` | Identity | Источник истины единой даты рождения пользователя |
| `UserRole` | Identity | Авторизация и выбранные качества пользователя |
| `TeacherProfile` | Tutoring | Учебные и контактные данные преподавателя |
| `StudentProfile` | Tutoring | Учебные и контактные данные ученика |
| `Subject` | Tutoring | Справочник учебных предметов |
| `StudentInvitation` | Tutoring | Цель, срок и состояние приглашения |
| `TeacherStudent` | Tutoring | Подтверждённая связь |
| `LessonOccurrence`, участники и статистика | Scheduling | Уроки и расписание |
| Межмодульная координация | Workflows | Атомарные составные сценарии |
| Доставка писем | Notifications | SMTP и другие каналы доставки |

Наличие чужих данных в HTTP response не меняет владельца этих данных.

Дата рождения остаётся только в Identity. Workflow не передаёт её в Tutoring при регистрации или добавлении роли. Tutoring не хранит дату рождения и возраст: возраст вычисляется Identity на дату чтения профиля.

## 6. Модели учебных профилей

### 6.1 TeacherProfile

```text
TeacherProfile
├── userId: UUID
├── displayName: String
├── contactEmail: ProfileEmail
├── contactDetails: List<String>
├── subjectCodes: Set<SubjectCode>
├── description: String?
├── education: String?
├── experienceYears: Integer?
├── city: String?
└── photoUrl: URI?
```

Инварианты:

- `userId` обязателен и уникален;
- соответствующий пользователь имеет роль `TEACHER`;
- `displayName` обязателен и не является пустым;
- `contactEmail` обязателен и нормализован;
- каждый `SubjectCode` существует в справочнике;
- набор `subjectCodes` содержит минимум один уникальный код;
- `experienceYears`, если указан, не может быть отрицательным;
- профиль не содержит пароль, account status, JWT или refresh token.

### 6.2 StudentProfile

```text
StudentProfile
├── userId: UUID
├── displayName: String
├── contactEmail: ProfileEmail
├── contactDetails: List<String>
├── subjectCodes: Set<SubjectCode>
└── photoUrl: URI?
```

Инварианты:

- `userId` обязателен и уникален;
- соответствующий пользователь имеет роль `STUDENT`;
- `displayName` обязателен и не является пустым;
- `contactEmail` обязателен и нормализован;
- набор `subjectCodes` может быть пустым, но каждый переданный код уникален и существует в справочнике.

### 6.3 Данные аккаунта и данные профиля

```text
Identity.firstName + lastName ≠ Tutoring.displayName
Identity.email                ≠ Tutoring.contactEmail
```

При создании профиля frontend получает имя аккаунта и подтверждённый account email через разрешённый составной API и подставляет их как начальные значения. Пользователь может подтвердить или изменить предложенные значения.

После сохранения профильные данные имеют независимый жизненный цикл. Изменение аккаунта не изменяет профиль автоматически, а изменение профиля не изменяет аккаунт.

Один пользователь с двумя ролями может иметь разные данные в двух профилях.

## 7. Контактный email профиля

`ProfileEmail` принадлежит `Tutoring`. Identity не владеет им, даже если его значение совпадает с `Identity.User.email`.

Пользователь указывает любой удобный для связи адрес. Tutoring проверяет его формат и сохраняет непосредственно в своём профиле. Адрес сразу показывается посетителям активного профиля. Он может совпадать с account email, но это не связывает их жизненные циклы. Изменение `contactEmail` не меняет `Identity.User.email`.

Подтверждение владения адресом существует только для account email в Identity. Приглашения связываются с аккаунтом по подтверждённому account email, а не по контактному адресу профиля.

## 8. Возраст в учебных профилях

`Identity.User.birthDate` хранится только в Identity. Владелец видит точную дату в данных своего аккаунта. Self-view и public-view Tutoring содержат только возраст в полных годах. Identity вычисляет его на дату запроса UTC через пакетный `findAgesByIds`; Tutoring не сохраняет ни дату рождения, ни возраст.

Публичный профиль доступен без связи для активного пользователя. Отсутствие связи ограничивает списки отношений и данные уроков. Summary остаётся минимальной межмодульной моделью без возраста.

### 8.1 Публичный поиск учебных профилей

Любой посетитель может открыть карточку активного преподавателя или ученика по
`userId` и искать активные профили по выбранному предмету и диапазону возраста.
Карточка содержит `age`, `displayName`, `contactEmail`, `contactDetails`, выбранные
предметы, фото и обычные поля соответствующей роли. Account email не
подставляется. Профиль с неактивным аккаунтом в Identity не показывается.

Выбранные предметы хранятся и читаются в TeacherProfile/StudentProfile.
`Subject` служит справочником допустимых кодов для формы и проверки записи.
Возраст вычисляется Identity на дату запроса UTC, а не хранится как
отдельное значение в Tutoring. Просмотр профиля не сообщает наличие приглашений, связей,
уроков или учебной статистики.

## 9. Семантика предметов

`Subject` является справочной сущностью Tutoring:

```text
Subject
├── code: SubjectCode
└── name: String
```

`subjectCodes` в `TeacherProfile` являются описанием основных направлений работы преподавателя. Они используются для:

- отображения специализации;
- информирования учеников;
- будущего поиска и фильтрации;
- предварительного заполнения или сортировки предметов в форме урока.

Они не являются набором разрешений.

```text
TeacherProfile.subjectCodes
= основные предметы преподавателя
≠ предметы, которые ему разрешено преподавать
```

Пример:

```text
TeacherProfile.subjectCodes = {MATH, PHYSICS}
Lesson.subjectCode = INFORMATICS
→ создание урока разрешено
```

При создании или изменении урока Scheduling проверяет только существование `SubjectCode` в справочнике Tutoring. Scheduling не проверяет наличие кода в `TeacherProfile.subjectCodes`.

Публичный API проверки предметов должен быть минимальным, поддерживать пакетную проверку и не раскрывать domain aggregates или persistence-модель.

## 10. StudentInvitation

```text
StudentInvitation
├── id: UUID
├── teacherUserId: UUID
├── studentEmail: InvitationEmail
├── studentUserId: UUID?
├── attachedAt: Instant?
├── status: InvitationStatus
├── createdAt: Instant
├── expiresAt: Instant
└── respondedAt: Instant?
```

```text
InvitationStatus
├── PENDING
├── ACCEPTED
├── REJECTED
└── EXPIRED
```

Разрешённые переходы:

```text
PENDING → ACCEPTED
PENDING → REJECTED
PENDING → EXPIRED
```

Из терминального состояния обратный переход запрещён.

`InvitationEmail` является зафиксированной целью приглашения. Он не становится account email или profile email. Автоматическое связывание приглашения с аккаунтом выполняется по подтверждённому нормализованному `Identity.User.email`.

Если незарегистрированный адресат открывает приглашение, регистрация из этого сценария показывает email приглашения в поле ввода и не позволяет изменить его. Это ограничение интерфейса помогает не потерять приглашение, но сервер всё равно привязывает его только после подтверждения того же account email в Identity. Регистрация с другим адресом возможна вне сценария приглашения, однако исходное приглашение к такому аккаунту не привяжется: преподавателю понадобится отправить новое приглашение на другой адрес. Открытие ссылки и начало регистрации не означают принятие приглашения.

Связывание приглашения с `studentUserId` фиксирует `attachedAt`: при известном адресате это `createdAt`, при поздней привязке — время операции. Оба поля либо заданы вместе, либо оба отсутствуют. Связывание не добавляет пользователю роль, не создаёт профиль и не означает принятие приглашения.

## 11. TeacherStudent

```text
TeacherStudent
├── teacherUserId: UUID
├── studentUserId: UUID
└── createdAt: Instant
```

Инварианты:

- пара `teacherUserId + studentUserId` уникальна;
- преподаватель имеет роль и профиль `TEACHER`;
- ученик имеет роль и профиль `STUDENT`;
- связь создаётся только после принятия приглашения;
- один преподаватель может иметь много учеников;
- один ученик может иметь много преподавателей;
- пользователь с обеими ролями рассматривается в каждой стороне согласно текущему сценарию;
- самоприглашение и связь пользователя с самим собой запрещены;
- связь удаляется только после обработки будущих уроков внешним workflow.

## 12. Участники сценариев

### Человеческие участники

- `Teacher` — активный пользователь с ролью `TEACHER` и `TeacherProfile`.
- `Student` — активный пользователь с ролью `STUDENT` и `StudentProfile`.
- `DualRoleUser` — пользователь с обеими ролями и двумя профилями.

### Системные участники

- `Identity` — аккаунт, источник истины даты рождения, роли, статус, JWT и account email.
- `Scheduling` — уроки и расписание.
- `Workflows` — регистрация, добавление второй роли, отвязка и составные запросы.
- `Notifications` — физическая доставка писем.
- Spring Security — проверка JWT и предоставление доверенного principal.

## 13. Каталог внутренних сценариев Tutoring

### TUT-01. Получение справочника предметов

**Актор:** любой посетитель; аутентификация не требуется.

**Поток:**

1. Загрузить доступные предметы.
2. Вернуть стабильный `code` и отображаемое `name`.
3. Не раскрывать persistence-данные.

**Результат:** справочник только для чтения.

### TUT-02. Получение собственного профиля преподавателя

**Актор:** `Teacher`.

**Вход:** `userId` из подтверждённого principal.

**Поток:**

1. Проверить роль `TEACHER`.
2. Найти `TeacherProfile` по `userId`.
3. Получить возраст через Identity API и вернуть собственный профиль.

Отсутствие профиля при существующей роли рассматривается как нарушение межмодульного инварианта, а не как обычный результат onboarding.

### TUT-03. Обновление профиля преподавателя

**Актор:** `Teacher`.

**Предусловия:** роль и существующий профиль принадлежат текущему пользователю.

**Поток:**

1. Получить `userId` из principal.
2. Проверить роль и активность через разрешённые security/Identity-контракты.
3. Проверить коды предметов пакетно.
4. Применить изменения профиля.
5. При изменении `contactEmail` проверить его формат.
6. Атомарно сохранить профиль и набор предметов.

Создание первоначального профиля выполняется только регистрационным или role-onboarding workflow.

### TUT-04. Получение собственного профиля ученика

Сценарий аналогичен TUT-02 и требует роль `STUDENT` и соответствующий профиль.

### TUT-05. Обновление профиля ученика

Сценарий аналогичен TUT-03. Дата рождения остаётся в Identity и не меняется через Tutoring.

### TUT-06. Создание приглашения ученику

**Актор:** `Teacher`.

**Вход:** email предполагаемого ученика.

**Предусловия:**

- аккаунт преподавателя активен;
- роль `TEACHER` и `TeacherProfile` существуют;
- приглашение не адресовано самому преподавателю;
- от этого преподавателя нет активного приглашения на тот же нормализованный email;
- подтверждённая связь ещё не существует.

**Поток:**

1. Получить `teacherUserId`.
2. Нормализовать email по согласованному с Identity правилу.
3. Попытаться найти аккаунт по подтверждённому account email.
4. Создать приглашение на 30 суток.
5. Если аккаунт найден, заполнить `studentUserId` и установить `attachedAt = createdAt`, не принимая приглашение автоматически.
6. Сохранить приглашение.
7. Надёжно инициировать доставку письма после commit.

Приглашение можно создать для незарегистрированного адресата. Если найденный пользователь ещё не имеет роли `STUDENT`, приглашение остаётся ожидающим; для принятия пользователь должен сначала пройти student-onboarding.

### TUT-07. Связывание приглашений после подтверждения account email

**Инициатор:** публичное событие `identity.api.event.AccountEmailVerifiedEvent`.

**Поток:**

1. Получить `eventId`, `userId`, подтверждённый нормализованный account email и `verifiedAt`; повторно проверить актуальность адреса через публичный Identity API.
2. Найти действующие `PENDING`-приглашения на этот email; истёкшие и самоприглашения не привязывать.
3. Заполнить `studentUserId` и `attachedAt` временем привязки.
4. Сохранить статус `PENDING`.
5. Не создавать `TeacherStudent`.

Приглашения не связываются с аккаунтом до подтверждения владения его email. Обработчик сохраняет обработанный `eventId`, поэтому повторная доставка события не изменяет результат.

### TUT-08. Получение входящих приглашений

**Актор:** аутентифицированный пользователь, к которому привязано приглашение; роль `STUDENT` и StudentProfile для просмотра не требуются.

**Поток:**

1. Получить `studentUserId`.
2. Найти только приглашения, связанные с этим пользователем.
3. Вычислить эффективный статус на момент `asOf` без изменения сохранённого статуса; учитывать только приглашения с `attachedAt <= asOf`.
4. Пакетно получить данные профилей преподавателей.
5. Вернуть cursor-страницу.

Если роли `STUDENT` и StudentProfile ещё нет, список остаётся доступным; перед принятием пользователь проходит student-onboarding.

### TUT-09. Принятие приглашения

**Актор:** аутентифицированный адресат приглашения.

**Предусловия:**

- приглашение принадлежит текущему пользователю;
- статус равен `PENDING`;
- срок не истёк;
- пользователь активен;
- `StudentProfile` существует; наличие роли обеспечивает согласованный workflow Identity, Tutoring не перепроверяет её при ответе;
- связь ещё не существует.

**Транзакционный поток:**

1. Загрузить приглашение с защитой от конкурентного изменения.
2. Проверить ownership, статус и срок.
3. Перевести приглашение в `ACCEPTED`.
4. Установить `respondedAt`.
5. Создать `TeacherStudent`.
6. Сохранить оба изменения одной транзакцией.

Уникальное ограничение пары преподаватель–ученик является последней защитой от гонки.

### TUT-10. Отклонение приглашения

**Актор:** аутентифицированный адресат приглашения; роль `STUDENT` и StudentProfile для отказа не требуются.

Разрешён только переход:

```text
PENDING → REJECTED
```

Сценарий проверяет ownership, статус и срок, устанавливает `respondedAt` и не создаёт связь.

### TUT-11. Истечение приглашений

Разрешён переход:

```text
PENDING → EXPIRED
```

Истечение проверяется при каждой операции с приглашением. В v1 отдельной плановой задачи материализации `EXPIRED` нет: списки вычисляют эффективный статус, а создание нового приглашения при необходимости материализует старое истёкшее `PENDING` на тот же адрес.

### TUT-12. Получение учеников преподавателя

**Актор:** `Teacher`.

Источники данных:

```text
TeacherStudent                  → Tutoring
StudentProfile                 → Tutoring
displayName и contactEmail      → Tutoring
age                             → IdentityQuery.findAgesByIds
```

Правила:

- возвращаются только ученики текущего преподавателя;
- контактные данные доступны и в публичном профиле;
- `age` вычисляется Identity пакетно на дату чтения;
- точная дата рождения не передаётся в Tutoring;
- используется cursor pagination.

### TUT-13. Получение преподавателей ученика

Зеркальный сценарий TUT-12. Список отношений возвращает только преподавателей текущего ученика. Их публичные профильные данные доступны и отдельно, без связи.

### TUT-14. Проверка одной связи

**Потребители:** Scheduling и Workflows.

**Вход:** `teacherUserId`, `studentUserId`.

**Результат:** минимальный ответ о наличии подтверждённой связи. Aggregate и структура хранения не возвращаются.

### TUT-15. Пакетная проверка связей

**Потребитель:** Scheduling при создании группового урока.

**Вход:** `teacherUserId` и набор `studentUserIds`.

**Результат:** подтверждение всех связей либо контролируемая ошибка с неподтверждёнными учениками. Проверка выполняется одним пакетным вызовом.

### TUT-16. Проверка существования предметов

**Потребители:** Scheduling, профильные use cases и Workflows.

**Вход:** один или несколько `SubjectCode`.

**Результат:** подтверждение существования всех кодов либо ошибка с неизвестными кодами.

Сценарий не принимает `teacherUserId` и не проверяет наличие предмета в `TeacherProfile.subjectCodes`.

### TUT-17. Получение минимальных межмодульных моделей профиля

**Потребители:** Workflows и query facades.

Tutoring возвращает immutable public models с минимальным набором необходимых данных. Domain aggregates, HTTP DTO и jOOQ records наружу не передаются.

### TUT-18. Удаление подтверждённой связи

**Потребитель:** только доверенный `UnlinkStudentWorkflow`.

**Предусловие:** Scheduling успешно обработал будущие уроки.

**Поток:**

1. Проверить существование связи.
2. Удалить `TeacherStudent`.
3. Зафиксировать результат.

Сценарий не вызывает Scheduling самостоятельно.

### TUT-19. Изменение контактного email профиля

Сценарий существует отдельно для `TeacherProfile` и `StudentProfile`.

**Поток:**

1. Проверить ownership профиля.
2. Проверить формат нового email и нормализовать его.
3. Сохранить новый `contactEmail` в профиле в рамках обычного обновления.

### TUT-20. Реакция на подтверждение account email

**Инициатор:** публичное событие Identity:

```text
identity.api.event.AccountEmailVerifiedEvent
├── eventId: UUID
├── userId: UUID
├── email: String
├── purpose: REGISTRATION | EMAIL_CHANGE
└── occurredAt: Instant
```

Обработчик связывает ожидающие приглашения с `userId`. Он идемпотентен по `eventId`. Подтверждение account email не меняет `contactEmail` профиля. Событие сообщает подтверждённый факт и не даёт Tutoring доступа к агрегату или таблицам Identity.

### TUT-21. Создание первоначального профиля через публичный command API

Этот сценарий не доступен frontend напрямую. Его вызывают только `RegistrationWorkflow` и `RoleOnboardingWorkflow` через `tutoring.api.command.profile.TutoringProfileCreationCommands`. Команда содержит `userId` и один или два набора профильных данных без даты рождения.

Он:

1. проверяет отсутствие профиля этого типа;
2. проверяет профильные данные и предметы;
3. создаёт профиль для явно переданного `userId`;
4. не создаёт и не изменяет роль самостоятельно.

Точный повтор составного запроса обрабатывает Workflows до вызова Tutoring. Повторный вызов команды создания уже существующего профиля сам по себе отклоняется.

## 14. Публичные контракты Identity для Tutoring и Workflows

Tutoring и Workflows используют только `identity.api`. Доступ к application-портам, domain-моделям, репозиториям и таблицам Identity запрещён.

```text
identity.api.query.IdentityQuery
├── findUserById(userId)
├── findUsersByIds(userIds)
├── findUserByVerifiedEmail(normalizedEmail)
├── findActiveUserIds(userIds)
└── findAgesByIds(userIds, asOf)

identity.api.IdentityRegistrationGateway
└── register(RegistrationData) → RegistrationReceipt(userId, email, verificationExpiresAt)

identity.api.IdentityRoleGateway
└── addRole(AddUserRoleCommand)

identity.api.event.AccountEmailVerifiedEvent
└── eventId, userId, email, purpose, occurredAt
```

Identity вычисляет возраст пакетно, не раскрывая дату рождения другим модулям. Проверка связи нужна для списка отношений и статистики уроков, а не для публичного возраста.

## 15. Межмодульные сценарии

### WF-01. Регистрация с ролями и профилями

```text
Registration request
→ RegistrationWorkflow
→ проверить соответствие roles ↔ profiles и ключ повтора запроса
→ IdentityRegistrationGateway.register(...)
→ передать созданный userId и профильные данные в TutoringProfileCreationCommands.createInitialProfiles(...)
→ Notifications сохраняет delivery request
→ commit
→ SMTP-отправка подтверждения email после commit
```

Если выбрана одна роль, передаётся один профиль. Если выбраны обе роли, обязательны оба профиля.

`RegistrationController` находится в `workflows.registration.presentation`. `RegistrationWorkflow` открывает общую транзакцию PostgreSQL через единый `PlatformTransactionManager`. Identity и Tutoring проверяют собственные правила и участвуют в этой транзакции с propagation `MANDATORY` или согласованным `REQUIRED`. Ошибка любого шага откатывает создание пользователя, ролей, профилей и delivery request. SMTP и обработчики публичных событий выполняются только после commit.

### WF-02. Добавление второй роли

```text
Нажатие «Стать учеником/преподавателем»
→ заполнение соответствующего профиля
→ RoleOnboardingWorkflow
→ проверить соответствие новой роли типу профиля и ключ повтора запроса
→ IdentityRoleGateway.addRole(...)
→ вызвать TutoringProfileCreationCommands.createTeacherProfile(...) или createStudentProfile(...)
→ commit
→ refresh access JWT
```

Роль, профиль и запись о результате составного запроса создаются атомарно в общей транзакции Workflows.

### WF-03. Отвязка ученика

```text
Teacher request
→ UnlinkStudentWorkflow
→ TutoringQuery.requireLinked(...)
→ SchedulingManagement.processFutureLessonsForUnlink(...)
→ TutoringManagement.removeTeacherStudent(...)
→ commit
```

Scheduling:

- отменяет будущие индивидуальные уроки;
- удаляет ученика из будущих групповых уроков;
- преобразует группу с одним оставшимся учеником в индивидуальный урок.

Связь удаляется последней. Ошибка любого шага откатывает весь сценарий.

### QF-01. Карточка ученика преподавателя

```text
Identity   → разрешённые account data, если они нужны сценарию
Tutoring   → профиль, связь и контакты
Identity   → возраст через пакетный query
Scheduling → статистика уроков
```

Ответ собирает внешний `StudentCardQueryFacade`, чтобы Tutoring не зависел от Scheduling. Публичные сведения он получает из активного `StudentProfile`, возраст — через Identity API; связь проверяется отдельно перед выдачей статистики уроков. Точная дата рождения не передаётся.

### QF-02. Составной GET /me

```text
Identity → данные аккаунта, roles, account status
Tutoring → TeacherProfile и/или StudentProfile
```

Ответ собирает внешний `MeQueryFacade` через публичные query API модулей. Identity не должен зависеть от внутренних классов Tutoring.

## 16. Авторизация и ownership

| Операция | Требование доступа | Дополнительная проверка |
|---|---|---|
| Получение собственного TeacherProfile/StudentProfile | Роль сверяет составной `MeQueryFacade` | `principal.userId` совпадает с запрошенным self-view; роль без профиля — ошибка целостности |
| Обновление TeacherProfile/StudentProfile | Аутентифицированный владелец | Наличие соответствующего профиля и `profile.userId == principal.userId`; Tutoring не повторяет проверку роли в Identity |
| Создание приглашения | `TEACHER` | TeacherProfile принадлежит principal |
| Входящие приглашения | Аутентификация; роль `STUDENT` не требуется | `invitation.studentUserId == principal.userId` |
| Принятие | Аутентификация; StudentProfile обязателен | ownership приглашения, срок и состояние |
| Отклонение | Аутентификация; StudentProfile и роль `STUDENT` не требуются | ownership приглашения, срок и состояние |
| Список учеников/преподавателей | Аутентификация и профиль соответствующего типа | связи принадлежат текущему пользователю |
| Справочник предметов | Не требуется | публичное чтение без пользователя |
| Добавление второй роли | Любая текущая роль | пользователь изменяет только собственный аккаунт через workflow |

Проверка роли в JWT не заменяет ownership-проверку в application-сценарии. Для критичных изменений application может дополнительно проверить актуальные роль и статус через Identity API.

После добавления второй роли frontend обязан получить новый access JWT через refresh, поскольку старый JWT содержит прежний набор ролей.

## 17. Транзакционные границы и идемпотентность

Атомарно выполняются:

- создание пользователя, выбранных ролей и всех выбранных профилей;
- добавление второй роли и создание соответствующего профиля;
- сохранение профиля и его набора предметов;
- принятие приглашения и создание `TeacherStudent`;
- межмодульная обработка уроков и удаление связи.

Идемпотентными должны быть:

- повторная доставка событий регистрации и подтверждения email;
- привязка ожидающих приглашений;
- точный повтор составного workflow-запроса без нового добавления роли;
- повторная доставка команды уведомления;
- безопасное повторение onboarding-запроса после неопределённого сетевого результата.

Ограничения базы данных остаются последней защитой от конкурентных запросов.

Для регистрации и добавления роли Workflows сохраняет ключ повтора, fingerprint и результат всего запроса; команды Identity и Tutoring не ведут отдельные журналы этих операций. В модульном монолите согласованность обеспечивает общая транзакция. Отвязка и самостоятельные операции Tutoring могут использовать собственный `operationId`.

## 18. Сквозные инварианты

- У пользователя есть минимум одна образовательная роль.
- Каждой образовательной роли соответствует ровно один профиль.
- Профиль не может существовать без соответствующей роли.
- Один `TeacherProfile` и один `StudentProfile` на `userId`.
- `Identity.User.birthDate` хранится только в Identity и доступна владельцу аккаунта.
- Tutoring не хранит дату рождения или возраст; профиль активного пользователя показывает возраст, вычисленный Identity.
- Профильный и account email являются разными данными с разными жизненными циклами.
- `contactEmail` профиля проверяется по формату и показывается публично без подтверждения владения адресом.
- Каждый код предмета существует в справочнике Tutoring.
- `TeacherProfile.subjectCodes` не ограничивает предметы уроков.
- Активное приглашение преподавателя на нормализованный email уникально.
- Самоприглашение запрещено.
- Привязка приглашения к аккаунту не означает принятие.
- Терминальный статус приглашения нельзя изменить.
- Пара преподаватель–ученик уникальна.
- Связь создаётся только после принятия приглашения.
- Связь удаляется только после успешной обработки будущих уроков.
- Другие модули не читают таблицы Tutoring напрямую.
- Tutoring не читает таблицы Identity и Scheduling напрямую.

## 20. Функции, не входящие в первую версию

- удаление образовательной роли;
- удаление учебного профиля;
- ручное создание связи без приглашения;
- приглашение преподавателя учеником;
- отмена приглашения преподавателем;
- повторная отправка существующего приглашения отдельной командой;
- администрирование справочника предметов через пользовательский REST API;
- ранжированный каталог преподавателей с расширенными фильтрами;
- публичное отображение точной даты рождения;
- платежи, домашние задания и история обучения;
- хранение статистики уроков в Tutoring.

## 21. Критерий завершения этапа

Этап считается завершённым после фиксации следующих решений:

- границы и владельцы данных определены;
- обязательные роли и связь роли с профилем определены;
- регистрация и добавление второй роли отнесены к Workflows;
- модели профилей и владение контактами определены;
- `birthDate` хранится только в Identity; Tutoring показывает вычисленный возраст активного профиля;
- предметы профиля признаны описательными, а не разрешительными;
- внутренние и межмодульные сценарии перечислены;
- публичные command/query/event API Identity, необходимые Workflows и Tutoring, определены;
- общая транзакция и идемпотентность составных запросов в Workflows определены;
- запрещённые зависимости и сценарии вне объёма перечислены.
